## やりたかったこと

外出先で, スマホから自宅の PC のターミナルを触りたい, とずっと思っていました.

きっかけはコーディングエージェントです. 「あのリポジトリのあれ, 直しておいてほしいな」と電車の中で思いつくことがそこそこあって, そのたびに家に帰るまで覚えておくか, メモしておいて忘れるかの二択になっていました. 手元の端末で回せるなら, 思いついた瞬間に投げて, あとは結果だけ見に行けばいい.

やりたいことは要するにこれだけです.

- スマホから自宅 PC のシェルが触れる
- **スマホ側から** セッションを起こせる
- 画面を閉じても, 電波が切れても, 走っているものが死なない

## Claude Code の Remote Control では届かなかったところ

まず既存の手段を見ました. Claude Code には [Remote Control](https://code.claude.com/docs/en/remote-control) があります. 手元のマシンで走っている Claude Code のセッションに, スマホの Claude アプリや claude.ai/code からつなげる機能です.

これはよくできていて, 実際やりたいことのかなりの部分を満たします. デスクで始めたタスクをソファでスマホから引き継ぐ, という体験はそのまま提供されています. コードの実行もファイルアクセスも自分のマシンに閉じたままなのも good.

ただ, 自分の使い方には二点ほど噛み合いませんでした.

**一つ目.** セッションの立ち上げが PC 側からになります. CLI で `claude remote-control` を叩くか, VS Code 拡張のコマンドを使うかで, サーバーモードならそのプロセスがターミナルに居座って接続を待ち受け, セッション URL と QR コードを出してくれる, という作りです.

つまり **家を出る前にセッションを立ち上げておく必要がある.** 立ち上げ忘れて出てしまったら, その日は諦めるしかない. 自分がやりたかったのは「外に出てから思いついたときに, その場で起こす」ことだったので, ここが一番効きました.

**二つ目.** これは Claude Code のセッションであって, 素のシェルではありません. 「ついでにログを見たい」「ディスクの空きを確認したい」といった雑用が, 同じ導線に乗ってきません.

Remote Control が悪いという話ではまったくなくて, 単に自分の欲しかったものが少しずれていた, というだけです. こちらが欲しかったのは **スマホから起こせる, 素のターミナル** でした.

## 素朴にやると, セッションがブラウザに紐づいて死ぬ

最初は素朴に, web ベースのターミナルを自宅のデスクトップでサービスとして立てて, スマホのブラウザからつなぎました. 動くには動きます.

ただ, セッションがブラウザのプロセスに紐づいているのが問題でした.

- ブラウザのタブが OS に落とされる
- アプリがアグレッシブにバックグラウンド化される
- 電車に乗って電波が一瞬切れる

このどれが起きても PTY ごと死んで, やり直しになります. 短いコマンドを打つだけならまだ諦めがつくのですが, 長時間動くエージェントを回している最中に切れると, その実行自体が失われます. 「思いついた瞬間に投げて, あとは結果だけ見に行く」がやりたかったのに, 投げたあと画面を閉じられないのでは意味がない.

## 発想の反転: セッションの状態をクライアントから剥がす

最初に考えたのはクライアントを賢くする方向でした. 再接続を実装して, 切れている間のバッファを持っておいて, 復帰したら差分を流し込む. ただこれは要するに端末の状態機械をクライアント側にもう一つ作るということで, どう考えても大変な割に壊れやすい.

そこで逆にしました. **クライアントがセッションを持たない設計にする.**

サーバー側に長命な tmux セッションを置いて, そこに PTY で attach するだけの小さなサーバーを立てます. アプリ側はバイトを運んで描画するだけの端末レンダラに徹して, attach と detach しかしない.

これで一番効いた性質がこれです.

> **tmux セッションはクライアントより長生きする.**

バックグラウンド化も, 回線断も, アプリのプロセス kill も, 走っているプロセスには一切触れません. 再接続は「同じセッションに attach し直す」だけで済みます. そして, セッションを作るのもスマホから叩ける普通の API になったので, 最初にやりたかった「外に出てから起こす」も満たせました.

嬉しかったのは, バッファの復元を自分で書かなくてよくなったことでした. 「切れている間の出力をどこかに貯めておいて復帰時に流す」というのは tmux が既にやっていることなので, そこに乗るだけでいい. 複数のクライアントが同じセッションを見たときの挙動も, tmux のセマンティクスがそのまま答えになります.

自前で持つ状態を減らすと, 考えるべきことがまるごと消えてくれる, という当たり前のことを久しぶりに強く実感しました.

## 「つながっているのに画面が真っ黒」

ここが一番ハマったところです.

接続は成功する. ステータスも open になる. なのに画面は真っ黒のままで, キーを叩いても何も起きない. サーバー側のログを見てもエラーは出ていない.

原因は一本道ではなく, 連鎖していました.

1. 端末のサイズ (rows / cols) をサーバーに伝える resize メッセージを, 描画側が **起動時に一度だけ** 送る作りになっていた
2. その一度が, WebSocket がまだ `CONNECTING` の最中に飛ぶことがある (コールドスタート時や, 再接続した直後)
3. 送信側は, open していないソケットへの送信を **黙って捨てていた**
4. 結果, PTY は tmux のデフォルトサイズのままになる
5. そして新しく attach したときのサイズが, tmux が既に持っているサイズと一致してしまう. サイズが変わっていないので **SIGWINCH による再描画が発火しない**
6. 端末エミュレータには何も届かない. 真っ黒

面白いのは 5 でした. 「サイズが変わっていないなら再描画しない」という tmux 側の最適化はどう見ても正しくて, その正しさがこちらのバグを覆い隠していました. サイズは間違っているのだけれど, 間違ったまま前回と一致しているので, 誰も文句を言わない.

3 の「黙って捨てる」も相当たちが悪かったです. ここでエラーが出ていれば 10 分で終わっていた話でした.

直し方自体は単純で, 最後に送ろうとした resize を覚えておいて, ソケットが open するたびに再送するようにしました. **一度だけ送るハンドシェイクを, 毎回リプレイする状態に変えた** ということです.

一般化するなら, 接続が確立する前に送られうるメッセージを送りっぱなしにしてはいけない, ということだと思っています. 送信を fire-and-forget にしていいのは, 送信経路が確実に生きているときだけです.

## OS はアプリを生かしてくれない

セッションは死ななくなりました. 次に問題になったのは通知です.

エージェントの実行が終わったらスマホに知らせてほしいのですが, バックグラウンドに回ったアプリは数秒から数分で吊るされます. しかもこの時間は OEM 依存で, 端末によって全然違う. そうなると通知のために張っている WebSocket が死んで, その間に飛んできたイベントが黙って失われます.

Android の対策としてはフォアグラウンドサービス (FGS) を使うことになります. 「ユーザーから見える通知を出し続ける」代わりに「プロセスを生かし続ける」契約を OS と結ぶ仕組みです. なので低優先度の常駐通知を一つ出しています.

ただ, ここに落とし穴がありました.

使っている通知ライブラリが同梱している FGS の宣言が `shortService` 型で, これには **システム側に約 3 分のハード上限** があります. 3 分経ったら, こちらの JS が何をしていようが問答無用でサービスが殺されます.

`dataSync` 型にすれば数時間まで伸ばせます. ただしそのためにはライブラリが同梱している `AndroidManifest.xml` にパッチを当てる必要があり, つまりカスタムの config plugin を書くことになる.

ここは 3 分で妥協しました. 想定している使い方では, エージェントの応答はだいたい 1〜2 分で返ってきます. 3 分あれば大抵は間に合う. 上限に張り付くケースが実際に増えてきたら plugin を書く, という判断です.

制約を回避するコストと, 制約に当たる頻度を天秤にかける, というだけの話ではあるのですが, 「ライブラリの内部宣言が原因で上限が決まっている」という理由は外から見えません. コメントとして残しておかないと半年後の自分が確実に忘れると思って書き残しました.

## 通知のために, 設定を一切増やさない

通知そのものは, エージェント側のフック機構から叩けば済みます.

問題は, フックスクリプトが「どのサーバーに」「どのセッションとして」投げるかを知る必要があることでした. ここで設定ファイルをもう一つ置かせるのは避けたかった. セットアップの手数が増えるし, セッション ID のような動的な値を静的なファイルに書くのは筋が悪い.

解決策は環境変数の継承でした.

tmux セッションを作るときのプロセスの環境変数に必要な値を流し込んでおくと, **その tmux サーバーから生えるすべてのシェルがそれを受け取ります.** フックスクリプトは自分が動いている環境からそのまま読めるので, 追加の設定ファイルが要らない. セッション ID も, セッションを作った側が知っている値をそのまま渡せます.

フック側のシェル一行にも, 意図的に防御を入れました.

- **環境変数が無いときは何もしない.** このツールを経由せずにエージェントを起動したとき (普通にラップトップで動かしたときなど) に誤爆させないため
- **失敗を全部握り潰す.** ネットワークがタイムアウトしても, サーバーが落ちていても, そもそも `curl` が無くても, 黙って成功扱いで抜ける. 通知が失敗したせいでエージェントのセッションが止まるのは論外なので
- **コメントを冪等マーカーとして埋め込む.** セットアップを再実行したときに, 重複追加ではなく置換になるようにするため

二つ目が特に大事だと思っています. 通知は「失敗してもいい機能」なので, 失敗したときに本体を巻き込まないことを最優先にしました. 付加機能が本体の可用性を下げるのは本末転倒です.

## これは要するにリモートシェルである

最後に, 書いておきたかったことを.

作ったものは, 率直に言えば **ホストに対するリモートシェルアクセス** です. トークンを持っている人は任意のコマンドを実行できるし, 任意のファイルを読めます. 便利機能の皮をかぶっていますが, 実体は SSH の秘密鍵と同じ扱いをするべきものです.

冒頭に書いた Remote Control が「コードの実行もファイルアクセスも自分のマシンに閉じたまま」と明記しているのと同じ話で, 自分で作る場合はその境界を自分で引くことになります.

なので,

- インターネットに直接晒さない. 信頼できる LAN か, プライベートなトンネル (Tailscale / WireGuard / SSH) の後ろに置く
- デフォルトの平文トランスポートのまま, 信頼できない経路に出さない

自分しか使わないツールであっても, ここは README の目立つところに書くことにしました. 「便利なツール」として紹介文を書くと, この性質は確実に読み飛ばされます. 自分で書いておかないと, 半年後に「まあ大丈夫だろう」と言ってポートを開ける未来が見えたので.

## まとめ

- やりたかったのは「外出先のスマホから, 自宅 PC のターミナルを触る」こと. Remote Control は近いが, セッションの立ち上げが PC 側なので「出てから思いつく」には応えてくれなかった
- セッションの状態をクライアントから剥がすと, モバイル特有の「勝手に殺される」問題の大半が消える. tmux に預けるとバッファ管理を自分で書かなくて済む
- 接続が確立する前に送られうるメッセージは, 送りっぱなしにせず状態として持って毎回リプレイする
- OS の制約は, 回避コストと実際に当たる頻度を天秤にかけて妥協していい. ただし理由はコードに残す
- 環境変数の継承は, 設定ファイルを増やさずに文脈を渡す手段になる
- 付加機能は, 失敗しても本体を巻き込まないように作る
- 便利さの裏側がリモートシェルなら, そう書く
